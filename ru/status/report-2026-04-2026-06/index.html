Обновление кластера

Продолжается работа по обновлению программного обеспечения, работающего на машинах кластера FreeBSD.org. Мы начали размещать рабочие нагрузки на stable/15. В рамках этой работы некоторые рабочие нагрузки переносятся на разные машины. Эта работа продолжается на конец квартала.

Команда clusteradm обновляет рабочие сборщики пакетов (около 35 физических машин) с периодичностью примерно раз в шесть-восемь недель. На этих машинах работают снимки current ветки FreeBSD.

Другие машины обновляются по мере необходимости, с учётом исправлений безопасности в зависимости от степени их доступности извне.

На момент написания этого отчёта в кластере насчитывается 142 физические машины. У нас 42 машины на current, 21 на stable/15 и 73 на stable/14.

Сбор данных для больших языковых моделей

Инфраструктура Проекта FreeBSD продолжает подвергаться постоянным атакам со стороны сборщиков данных для обучения больших языковых моделей («ИИ»). Компании, обучающие эти модели, в значительной степени перенесли операции по сбору данных со своей собственной — легко идентифицируемой — инфраструктуры на ботнеты («резидентные прокси»), что затрудняет их блокировку на сетевых границах без значительного сопутствующего ущерба. Команда администраторов кластера снова потратила значительное количество времени в этом квартале на смягчение этих распределённых атак типа «отказ в обслуживании».

Команда Bugmeister

Ссылки:
FreeBSD Bugzilla URL: https://bugs.freebsd.org/ Общее количество открытых ошибок во времени URL: https://bugs.freebsd.org/bugzilla/page.cgi?id=showreport.html&type=total_open_bugs_over_time

Контактное лицо: Bugmeister <bugmeister@FreeBSD.org>

В этом квартале нам удалось снизить количество сообщений о проблемах (Problem Reports).

Хотя мы по-прежнему получаем патчи для дерева исходных кодов (src), большинство получаемых патчей относится к портам. Возможно, это связано с внедрёнными нами настройками автоуведомлений.

Для дерева src за последние 180 дней мы получили 643 новых сообщения о проблемах и закрыли 844. Для портов эти цифры составили 3493 и 4375 соответственно.

В настоящее время мы не ведём статистику о том, сколько из них действительно приводят к коммитам, хотя мы полагаем, что это число не является незначительным.

За тот же 180-дневный период Марк Линимон (Mark Linimon) и Торстен Цюльсдорф (Torsten Zuehlsdorff) продолжали работу по классификации (триажу) старых сообщений о проблемах. Работа Марка частично финансировалась Фондом FreeBSD в 2025 году. Результаты этой работы видны по двум последним спадам на нашем графике Общее количество открытых ошибок во времени.

Кроме того, в этом году мы, похоже, привлекаем больше внимания со стороны различных разработчиков FreeBSD (коммиттеров). Пожалуйста, свяжитесь с bugmeister, если вы заинтересованы в помощи.

Конечно, мы всё ещё лучше справляемся с классификацией сообщений, чем с привлечением внимания к уже имеющимся. Предложения приветствуются.

Марк Линимон взял на себя долгосрочный проект по обеспечению применимости всех отправленных патчей. Однако он не претендует на роль специалиста по контролю качества и не может самостоятельно оценивать их пригодность.

Полное управление CPUID для bhyve

Контактное лицо: Hans Rosenfeld <rosenfeld@grumpf.hope-2000.org>

Обзор проекта

Текущая работа над этим проектом направлена на интеграцию существующей концептуальной реализации во FreeBSD и добавление следующих функций удобства использования:

  • удобный метод настройки для переопределения отдельных битов, частей или даже целых функций CPUID по мере необходимости с сохранением остальной информации о CPUID хоста или предварительно заданной конфигурации CPUID;

  • удобный метод настройки идентификатора гипервизора, сообщаемого bhyve;

  • набор предварительно заданных конфигураций CPUID на основе общих архитектурных уровней x86, возможно, также включающий набор данных CPUID для нескольких реальных моделей процессоров, и удобный метод настройки для выбора одного из них для виртуальной машины.

Изменения в течение последнего квартала

Расширения синтаксиса конфигурации bhyve

Существующий синтаксис файла конфигурации bhyve был ограничен присваиваниями узлам конфигурации, которые внутренне преобразовывались в древовидный набор списков nvlist.

Чтобы обеспечить более гибкую настройку с использованием предварительно заданных фрагментов файлов конфигурации, синтаксис файла конфигурации bhyve был дополнен двумя новыми возможностями:

  • В узел конфигурации можно добавить значение с помощью оператора +=. Если этому же узлу конфигурации уже было присвоено значение, новое значение добавляется к старому, разделяясь запятой.

  • Другой файл конфигурации можно включить с помощью директивы include. Поддерживаются абсолютные и относительные пути, но относительные пути интерпретируются как относительные к пути файла конфигурации, в котором находится директива включения.

Ещё более гибкая настройка CPUID

Механизм настройки CPUID был расширен для поддержки символических имён возможностей, где каждое имя соответствует определённому биту регистра для функции CPUID. Это особенно полезно для отдельных расширений системы команд или других опциональных возможностей, которые можно включать или отключать по желанию.

Таким образом, вместо настройки cpuid.0x00000001+=edx|=0x00040000 теперь можно просто написать cpuid.enable+=psn. Существует также соответствующая опция cpuid.disable для символических возможностей.

Использование битовых операций над регистрами CPUID, конечно, всё ещё поддерживается, поскольку не все возможности CPUID могут быть выражены в виде отдельных битов возможностей.

Использование архитектурных уровней x86

Архитектурные уровни x86 теперь реализованы как набор предварительно заданных фрагментов файлов конфигурации, причём каждый более высокий уровень строится поверх более низкого.

Чтобы проиллюстрировать это, вот как теперь выглядит x86-64-v3.cfg:

include x86-64-v2.cfg
cpuid.enable+=fma,movbe,osxsave,avx,f16c
cpuid.enable+=bmi1,avx2,bmi2
cpuid.enable+=abm

Модель процессора или архитектуры можно выбрать либо путём включения соответствующего файла конфигурации из /usr/share/bhyve/cpu в файл конфигурации bhyve, либо указав её в командной строке как часть конфигурации виртуального процессора: bhyve […​] -c 16,model=x86-64-v1 […​]

Ограничения CPUID

Чтобы предотвратить случайное включение возможностей CPUID для гостевого процессора, которые не поддерживаются хост-процессором, анализатор конфигурации CPUID был расширен списком ограничений CPUID, которые проверяются при установке или изменении значения определённого регистра CPUID.

Для любого регистра в функции CPUID ограничение может указывать, какие биты неизменяемы, а какие могут быть только очищены.

Ограничения проверяются после применения конфигурации CPUID.

Планы на следующий квартал

  • Реализовать переопределения для ограничений CPUID, чтобы игнорировать любые ограничения или предупреждать о нарушении ограничения вместо остановки настройки виртуальной машины.

  • Предоставить больше предварительно заданных конфигураций процессоров на основе реальных процессоров.

  • Аналогично установке архитектурного уровня x86, будет реализован механизм для переопределения идентификации гипервизора без необходимости ручного изменения битов CPUID.

  • Провести рецензирование всего набора изменений и включить его во FreeBSD.

  • devel/qemu для управления образами дисков

  • net/samba419 для общего доступа к файлам по SMB

Завершение работы над API дескрипторов процессов 2

Контактное лицо: Konstantin Belousov <kib@FreeBSD.org>

Ссылки:
sys: добавление pdopenpid(2) URL: https://reviews.freebsd.org/D57124
link pddupfd(2) https://reviews.freebsd.org/D57163

После добавления системных вызовов pdwait(2) и pdrfork(2) я обратил внимание на другие недостающие возможности, которые запрашивают прикладные программисты. Самым крупным запросом, по-видимому, является возможность получения дескриптора процесса для существующего процесса.

В настоящее время только один файловый дескриптор может ссылаться на внутреннюю структуру struct procdesc в ядре, что отчасти объясняет, почему интерфейс для открытия процесса по pid ещё не реализован. В ходе работы была добавлена возможность для procdescs иметь более одного файла, указывающего на них. Атрибуты, управляющие поведением procdesc, например, daemon (закрытие файла не завершает процесс), были перенесены из procdesc в файл.

Это изменение позволило расширить внутренние интерфейсы procdesc для реализации системного вызова man:pdopenid(2).

Возможность, реализованная, например, в дескрипторах pidfd в Linux, — это системный вызов pidfd_getfd(), который дублирует указанный файловый дескриптор из целевого процесса в вызывающий процесс. Реализация этого для FreeBSD, названная man:pddupfd(2), относительно проста после получения вспомогательной функции fget_remote(9).

Проблема возникла, когда был разработан алгоритм проверки привилегий, необходимых для выполнения операции. Ядро проверяет результат p_candebug(), чтобы определить, разрешено ли что-либо, что напрямую обращается к программным ресурсам удалённого процесса. Но результат p_candebug() действителен только пока удерживается блокировка целевого процесса. Кроме того, p_candebug() запрещает действия, если целевой процесс изменяет выполняемую программу с помощью man:execve(2), что может изменить привилегии процесса, если образ имеет set-uid или set-gid. В целом, простая проверка с помощью p_candebug() неадекватна, потому что мы не можем удерживать блокировку процесса на протяжении всего fget_remote().

Для этого был разработан механизм, обеспечивающий взаимное исключение между выполнением exec в целевом процессе и вызывающим процессом, названный execblock. Также были добавлены вспомогательные функции для получения ссылки на текущее vmspace процесса, чтобы избежать использования execblock, когда для действия требуется только согласованное адресное пространство цели, например, чтение строк процесса или копирование памяти процесса. Существующие места в системе, подверженные этой гонке, были идентифицированы, и использование execblock или интерфейсов ссылок на vmspace было применено по мере необходимости.

Затем man:pddupfd(2) был реализован с помощью fget_remote() и execblock.

Приостановка с сохранением состояния (suspend-to-idle) и поддержка режима сна S0ix находятся в процессе добавления во FreeBSD.

Это позволит современным ноутбукам Intel и AMD, некоторые из которых не поддерживают режим сна ACPI S3, переходить в состояния пониженного энергопотребления для увеличения времени работы от батареи.

В основном статус такой же, как в предыдущем квартале — работа всё ещё продолжается по сужению проблем с возобновлением NVMe и исправлению проблем с состояниями D-state.

Общий интерфейс управления питанием был закоммичен, а zzz(8) был переписан для его использования. Теперь ожидается, что вы будете использовать sysctl kern.power.supported_stype для получения списка поддерживаемых общих типов сна и устанавливать sysctl kern.power.suspend для указания типа сна, который должен использовать zzz(8).

В драйвер acpi_spmc было внесено множество мелких исправлений и улучшений.

Общая поддержка USB4 NHI также была закоммичена. Единственное, что осталось закоммитить для поддержки USB4, необходимой для входа в S0i3, — это сама процедура приостановки. Справочная страница thunderbolt(4) была обновлена, чтобы более чётко указать, что она предназначена только для поддержки входа в S0i3.

Была написана справочная страница для amdsmu(4), чтобы лучше объяснить, как диагностировать вход в S0i3.

После почти двухмесячной паузы мы исправили некоторые ошибки в прототипе сохранения образа, перебазировали его на актуальный код и пересмотрели интерфейс между ядром и загрузчиком возобновления EFI, что потребовало изменений с обеих сторон. Это привело к ряду изменений в общем коде приостановки/возобновления ACPI и попутным исправлениям. В настоящее время ведётся работа над загрузчиком EFI (этап 1). Был разработан набросок части ядра для возобновления (этап 2).

Состоялось ещё несколько обсуждений о том, как сохранять образ системы, сохраняя его согласованность, поскольку сама операция дампа изменяет память ядра. Цель состоит в том, чтобы сузить круг компонентов, которые могут мешать дампу, и определить, как предотвратить это вмешательство. В частности, похоже, что низкоуровневый код DMA и IOMMU может выполнять выделение памяти при определённых обстоятельствах, и пока неясно, может ли это произойти во время дампа. После того как это будет определено, мы постараемся устранить эти обстоятельства, если это возможно, в противном случае будем работать над механизмом, подобным снимкам состояния (snapshot). Помимо этого аспекта, механизм живого снимка состояния может быть полезен, поскольку он позволяет использовать любые средства ядра без ограничений для выполнения дампа и, в частности, устраняет необходимость в отдельной процедуре дампа для каждого драйвера диска.

Мы представили текущее состояние этой работы, связанные с ней проблемы и возможную реализацию механизма, подобного снимкам состояния, на BSDCan в июне и сделаем это снова на EuroBSDCon в сентябре.

Совместное управление производительностью процессора (CPPC) — это стандарт, введённый ACPI, позволяющий операционной системе управлять уровнями производительности и энергоэффективности процессоров благодаря абстрактной шкале производительности, в общем случае не связанной с уровнями частоты и более детализированной, чем они.

Работа возобновлена после очередного начала в ходе Хаккатона в Галифаксе в конце июня.

В разработке находятся:

  • Новые параметры минимальной, максимальной и желаемой производительности для драйвера Intel (hwpstate_intel(4)).

  • Обучение powerd(8) работе с этими параметрами и предоставление базовых политик для них.

  • Параметр для установки EPP (Предпочтение эффективности/производительности) для всех процессоров одновременно и, вероятно, аналогичные параметры для минимального, максимального и желаемого значений производительности.

  • Условное включение функциональности CPPC драйвера AMD (hwpstate_amd(4)) при наличии таблицы ACPI _CPC. Параметр позволит пользователям обходить эту проверку, а также, возможно, проверку на наличие функциональности CPPC, сообщаемой через CPUID.

  • Глобальный параметр профиля с предопределёнными значениями (например, «Сбалансированный», «Производительность» и т.д.), который устанавливает все остальные более детальные параметры. Явная установка детального параметра переключит профиль на «Пользовательский».

В конце июня было закоммичено несколько предварительных чисток и исправлений.

Настройки LinuxKPI 802.11

В рамках подготовительных работ для Realtek и Mediatek были улучшены различные детали реализации LinuxKPI 802.11:

  • Переработка chandef / chanctx: это определения канала, на котором мы работаем. Переработана эмуляция chandef и способ обновления контекстов; подготовка к поддержке нескольких chanctx и т.д.

  • Аппаратное шифрование TX: mt7921 отлично работал с программным шифрованием, но после включения аппаратного ускорения шифрования мы могли только принимать некоторые пакеты, но больше не могли отправлять корректные кадры. Оказалось, что в зависимости от типа ключа драйвер использует разные пути для ключей, и мы устанавливали оба ключа одинаково, по сути перезаписывая первый вторым. Исправлен аргумент, передаваемый при вызове установки ключа, чтобы избежать этой проблемы. Это также может помочь rtw8x, где мы видели периодические проблемы, связанные с MC-пакетами, но проверка всё ещё ожидается.

  • Скорости (rates): начато заполнение и обновление большинства полей скоростей в LinuxKPI 802.11 (кроме одного, который нужен только для mt7615). Часть этой работы была выполнена для rtw8x в конце прошлого года, а большая часть дополнена для Mediatek.

  • Исправлена проблема порядка совместимости: оказалось, что порядок некоторых событий, который мы реализовали, не полностью соответствовал ожиданиям некоторых драйверов. Хотя мы настраивали и синхронизировали различные части, связанные со скоростями, от net80211 до LinuxKPI 802.11 и до драйвера, одно обновление приходило слишком поздно, оставляя mt7921 с базовыми скоростями. Простое перемещение кода для вызова в другом порядке решило проблему и позволило получить пропускную способность 11n и 11ac.

Изменения в LinuxKPI:

В дополнение к частям 802.11 в LinuxKPI, есть также общая инфраструктура LinuxKPI, которая требует корректировок.

  • PAGE_IS_LKPI_PAGE: это проект по преобразованию раннего сокращения, согласно которому struct page из Linux сопоставляется 1:1 с нативной vm_page, в полноценную struct page из Linux с поддержкой vm_page. Это в основном необходимо для некоторых драйверов Mediatek mt76, но также drm-kmod наконец сможет отказаться от некоторых специфических для FreeBSD хаков после того, как это будет включено.

  • Функции отсоединения (очистки) PCI в LinuxKPI: драйвер Mediatek вызывал панику ядра при выгрузке или завершении работы. Оказалось, что различные процедуры очистки PCI в LinuxKPI были не совсем корректны, на что уже указывал комментарий в одной из частей. Мы исправили это, а также очистили часть файла. На момент написания отчёта рецензирование всё ещё продолжается, но мы надеемся, что по крайней мере основные части будут закоммичены в ближайшее время.

  • Код IDR в LinuxKPI используется некоторыми драйверами Mediatek mt76, но также используется в drm-kmod и ряде полунативных драйверов. К сожалению, этот фреймворк имеет известные проблемы (как показывает история) и больше не соответствует современным ожиданиям. Переписывание этого кода несколько сложно из-за большого влияния, но мы надеемся завершить его в начале 26Q3.

  • Улучшен и дополнен код lindebugfs(4) для возможности использования debugfs для отладки mt7921.

Поддержка Realtek rtw8x

После обновлений до Linux v7.0 проблемы с некоторыми чипсетами, не способными установить соединение, усилились. Как rtw88(4), так и rtw89(4) теперь демонстрируют различные проблемы. Была обнаружена дополнительная проблема: драйвер rtw88(4) для по крайней мере одного чипсета уходит в ожидание на 6 секунд, по сути приводя к тайм-ауту аутентификации. Поддержка Mediatek mt76

Продолжается работа по поддержке нескольких драйверов Mediatek mt76, в первую очередь mt7921 и mt7925. После нескольких улучшений LinuxKPI и LinuxKPI 802.11 можно сказать, что mt7921 передаёт пакеты с приемлемой пропускной способностью для первого этапа. mt7925 делает то же самое, но по крайней мере незавершённая работа над IDR в LinuxKPI приводит к нестабильности. mt7915 также требует IDR, но, кроме того, похоже, не поддерживает аппаратное сканирование, что означает, что нам нужно исправить программное сканирование как следует, что также поможет rtw8x, у которых есть странный запасной вариант программного сканирования в случае, если аппаратное сканирование недоступно. Другие чипсеты будут протестированы после того, как эти изменения будут включены и полностью активированы в main.

В дополнение к работам над LinuxKPI мы отладили одну панику, вызванную драйвером. Оказалось, что драйверы перепланируют некоторые работы во время отсоединения (завершения работы), но затем освобождают нижележащую память. Это оставляло запланированный вызов, и когда мы пытались обойти список вызовов, это вызывало панику.

Поддержка USB в LinuxKPI

В первом квартале мы сообщали о блокирующей проблеме для этого. Я рад сообщить, что половина проблемы была решена: опция компилятора, которую я изначально хотел добавить, теперь полностью удалена из дерева исходных кодов в main и stable/15. Теперь остаётся найти минималистичное решение для повторного введения этой функциональности, а не разносить её по всему ядру или множеству отдельных файлов. Ссылки:
Обновление до драйверов DRM из Linux 6.13 URL: https://github.com/freebsd/drm-kmod/pull/469

Контактное лицо: Jean-Sébastien Pédron <dumbbell@FreeBSD.org>

Драйверы DRM — это драйверы ядра для встроенных и дискретных графических процессоров. Они поддерживаются в ядре Linux, и мы портируем их во FreeBSD. На момент данного отчёта мы берём только драйверы DRM для AMD и Intel (драйверы NVIDIA для FreeBSD являются проприетарными и предоставляются самой NVIDIA).

Мы портируем их по одной версии Linux за раз. Это позволяет нам выпускать обновления чаще и упрощает портирование и отладку, поскольку дельта изменений меньше по сравнению с большим скачком через несколько версий.

В этом квартале мы завершили портирование драйверов DRM из Linux 6.12 LTS к моменту выхода FreeBSD 15.1-RELEASE. Поскольку это версия с долгосрочной поддержкой (LTS), мы будем отслеживать изменения в патчах Linux 6.12.x. В настоящее время мы находимся на версии 6.12.81, и ведётся работа по дальнейшему обновлению до последней версии патчей. Эти драйверы доступны в дереве портов и в виде пакетов.

В рамках работы над драйверами версии 6.12 было исправлено несколько ошибок или регрессий для уже поддерживаемых графических процессоров. Некоторые новые графические процессоры также начали работать.

Драйверы HID для Bluetooth

Ссылки:

Страница проекта в вики FreeBSD URL: https://wiki.freebsd.org/SummerOfCode2026Projects/BluetoothSupportForHIDDevices
Репозиторий проекта на Github URL: https://github.com/majintosh/freebsd-bthid

Контактное лицо: Majed Alkhaleefah <majed@FreeBSD.org>

Я работаю над двумя драйверами для обеспечения поддержки HID-драйверов для устройств Bluetooth в рамках GSoC 2026.

Основная цель этого проекта — регистрация подключаемых Bluetooth-устройств HID как устройств Newbus с помощью двух новых драйверов: bthidbus и bthid. bthidbus выступает в роли родительской шины, управляющей созданием и подключением дочерних устройств bthid. bthid служит транспортным уровнем, создавая устройство hidbus и перенаправляя на него все полученные пакеты после удаления их заголовков. Краткосрочная цель здесь — обеспечить поддержку беспроводных HID-подключений. Долгосрочная цель — начать закладывать основу, которая позволит другим писать драйверы для устройств, подключаемых только через Bluetooth.

Что было сделано:

  • bthidbus может успешно открывать соединение с Bluetooth-устройством через сокеты.

  • bthid может принимать сокеты, переданные от bthidbus через ivars, и управлять ими.

  • bthid может отправлять дескриптор отчёта в hidbus, который успешно создаёт соответствующее HID-устройство и драйвер. (например, геймпад, подключённый по Bluetooth, создаёт устройство hgame и узел evdev.)

  • Ввод с Bluetooth-устройств успешно принимается hidbus и evdev.

Текущие проблемы и планируемые изменения:

  • Фактические дескрипторы отчётов, Bluetooth-адреса и т.д. должны быть жёстко закодированы в bthidbus. Изначально я рассматривал возможность добавления логики запросов/прослушивания в bthidbus, чтобы он действовал как псевдо-сервер, но я опасался, что это приведёт к раздуванию кода и расширению области ответственности. Вместо этого я планирую положиться на существующую логику запросов демона bthidd и передавать новую информацию о подключении в bthidbus через ioctl. Это избавит bthidbus от текущей роли инициатора соединения и сделает его ответственным только за управление уже открытыми соединениями.

  • Наблюдается значительная задержка ввода при мониторинге через evtest. У меня есть две рабочие гипотезы. Первая заключается в том, что проблема кроется в bthid и в том, как он управляет прерываниями через очереди задач (taskqueues). Вторая — что проблема в сетевом стеке, поскольку Bluetooth-пакеты передаются через несколько различных узлов Netgraph перед тем, как быть полученными bthid. Также вполне возможно, что это проблема evtest; мне ещё предстоит это выяснить.

На данный момент все тесты проводились с контроллером Nintendo Switch Pro.

Поддержка ROCm во FreeBSD

Ссылки:

Форк rocm-systems с исправлениями для FreeBSD URL: github.com/Yohello1/rocm-systems

Контактное лицо: Sourojeet Adhikari <siri@racha.ca>

ROCm — это вычислительная платформа, используемая AMD для своих графических процессоров. На данный момент FreeBSD вообще не поддерживает ROCm ни на уровне инструментария, ни на уровне драйверов. Я работаю над изменением этой ситуации и переносом необходимых изменений в вышестоящие проекты.

Насколько мне известно, во FreeBSD есть несколько способов выполнять вычислительные задачи (такие как ИИ/МО, графика и т.д.) на графическом процессоре; эти способы, насколько мне известно, — это Vulkan и OpenGL. Как Vulkan, так и OpenGL достаточно хороши для вычислительных задач, в основном в графике, а иногда и в задачах машинного обучения. Но иногда существуют задачи, которые плохо подходят для Vulkan и OpenGL и вместо этого выполняются в ROCm/CUDA, поскольку ROCm и CUDA предоставляют разработчику гораздо больше контроля над выполнением задачи. Поэтому я пытаюсь внедрить поддержку ROCm во FreeBSD, чтобы мы могли запускать код/программы ROCm на FreeBSD. Для работы ROCm нам нужно несколько вещей. Первое — это форк LLVM от AMD, который я пропатчил, добился его работоспособности и отправил патчи в вышестоящий проект. Далее идут среды выполнения ROCm, которые были пропатчены, и в настоящее время я работаю над отправкой патчей в вышестоящий проект. Наконец, драйвер amdkfd, над патчингом которого я работаю и отправляю некоторые патчи, связанные с LinuxKPI, обратно в ядро FreeBSD.

За последнее время я отправил изменения в форк LLVM от AMD, позволяющие компилировать его во FreeBSD, чтобы вы могли собирать их инструментарий ROCm. Кроме того, я работал над внедрением серии патчей в LinuxKPI для постепенного добавления поддержки amdkfd.

Dockerbox — это виртуализированный демон Docker. Хотя демон Docker изначально недоступен во FreeBSD, Dockerbox запускает его внутри виртуальной машины Debian под управлением Bhyve, обеспечивая доступ к нему. Dockerbox поддерживает обычные функции Docker, такие как Docker Compose, публикацию портов и привязку монтирований (bind mounts). Этот проект направлен на упрощение использования Docker во FreeBSD в непроизводственных средах.

    Ещё не портирован.

  • freebsd-dockerbox-debian
    Кодовая база, используемая для создания дискового образа Dockerbox.
    Не портирован.

  • docker-cli
    Инструмент командной строки Docker CLI.
    v29.4.2 — портирован.

  • docker-compose
    Плагин Docker CLI для определения и запуска многоконтейнерных приложений.
    v5.1.3 — портирован.

  • docker-buildx
    Плагин Docker CLI, предоставляющий расширенные возможности сборки через BuildKit.
    v0.34.1 — портирован.

Ежемесячные отчёты о состоянии Kavocado – заметки по HPC во FreeBSD URL: https://kavocado.net/reports/

Контактное лицо: Generic Rikka <rikka.goering@outlook.de>

Этот отчёт продолжает инициативу по модернизации HPC-портов FreeBSD. Предыдущие кварталы были посвящены обновлению стека Slurm + PMIx + PRRTE + UCX и заполнению пробелов в сопутствующей экосистеме. Работа в этом квартале была сосредоточена на трёх вещах: поддержании основного планировщика и коммуникационных библиотек в актуальном состоянии в соответствии с быстро меняющимися релизами вышестоящих проектов, отправке накопившихся при поддержке этих портов исправлений переносимости для FreeBSD в вышестоящие проекты, чтобы локальные наборы патчей продолжали уменьшаться, и добавлении нового порта для MPI-параллельных утилит для работы с файлами, которые широко используются в больших HPC-файловых системах.

Выполненные работы

  • Дважды обновлён sysutils/slurm-wlm в этом квартале: с 25.11.4 до 25.11.5, а затем с 25.11.5 до 26.05.1, отслеживая последние вышестоящие релизы.

  • Исправлены несколько проблем времени выполнения, специфичных для FreeBSD, в net/ucx: улучшена обработка состояния асинхронных потоков, исправлена обработка перемещений UCM, исправлена привязка сокетов сигналов mm, а также решены другие проблемы переносимости времени выполнения для FreeBSD.

  • Обновлён net/ucx с 1.20.0 до 1.20.1, а также отдельно исправлена паника при ранней инициализации libucm вместе с несколькими сбоями в наборе тестов gtest, обнаруженными при проверке обновления.

  • Добавлен sysutils/mpifileutils как новый порт вместе со стеком зависимостей: devel/libcircle, devel/lwgrp и devel/dtcmp. Они предоставляют MPI-параллельные утилиты для работы с файлами (копирование, удаление, контрольные суммы и т.д.), обычно используемые в больших HPC-файловых системах.

  • Дважды обновлён benchmarks/py-reframe-hpc в этом квартале для отслеживания вышестоящих релизов фреймворка регрессионного тестирования.

  • Отправлены в вышестоящий проект UCX «UCS/TYPE: Исправления переносимости для сред без glibc/Clang», которые были рассмотрены и включены.

  • Открыт запрос на включение «UCS/SYS: исправления переносимости для платформ, отличных от Linux» в UCX, охватывающий определение размера буфера имени хоста, получение MAC-адреса через getifaddrs()/AF_LINK, сообщение об ошибках разделяемой памяти, перераспределение на основе mmap/munmap и запросы привязки потоков на основе cpuset_getaffinity(); в настоящее время обрабатываются замечания рецензентов.

  • Открыт запрос на включение исправлений переносимости в mpifileutils, ограничивающих использование Linux-специфичных API для FreeBSD и других сборок, отличных от Linux; в настоящее время на рассмотрении.

  • Совместно с SchedMD проведена работа над проверкой во время конфигурации Slurm для H5PTopen, используемой для обнаружения библиотеки высокого уровня HDF5, которая была включена в вышестоящий проект.

Работа в процессе

  • Обработка замечаний рецензентов по открытым запросам на включение исправлений переносимости в UCX и mpifileutils для их включения в вышестоящие проекты и дальнейшего уменьшения локальных наборов патчей в портах FreeBSD.

  • Продолжение сотрудничества с SchedMD для отправки в вышестоящий проект дополнительных исправлений переносимости, обнаруженных при поддержке sysutils/slurm-wlm во FreeBSD, включая улучшения обработки сокетов BSD.

  • Оценка дизайна плагина Slurm proctrack/freebsd_reaper, ставшего возможным благодаря недавно добавленной в ядро FreeBSD поддержке раскрытия метаданных реперера в информации о процессах.

  • Продолжение внимательного отслеживания вышестоящих релизов Slurm, UCX и PMIx/PRRTE для поддержания портов FreeBSD в актуальном состоянии с минимальным локальным патчированием.

Будущие планы

  • Включить ожидающие запросы на включение в вышестоящие проекты UCX и mpifileutils и продолжить выявление дальнейших проблем переносимости для отправки в вышестоящие проекты, а не для локального патчирования.

  • Создать прототип и отправить плагин Slurm proctrack/freebsd_reaper после завершения работы над соответствующим интерфейсом ядра.

  • Продолжить расширение экосистемы HPC-программного обеспечения, доступной в Коллекции Портов FreeBSD, и сокращение локальных наборов патчей во всём стеке везде, где возможно принятие вышестоящими проектами.

  • Документировать эталонное развёртывание Slurm + OpenMPI + PMIx + PRRTE + UCX на FreeBSD, чтобы снизить порог входа для новых организаций, экспериментирующих с FreeBSD в контексте HPC.
